# 통합 운영자 입장키 — 구현 명세 및 안전 기준

## 목적
운영자가 사전에 등록한 단일 ID/비밀번호로 로그인한 후 일반인(USER)과 변호사(LAWYER) 업무 흐름 및 운영 관리자 기능을 같은 작업 공간에서 검증한다. 업무 흐름을 평가하는 권한과 실제 고객 사건 접근권한·변호사 자격은 분리한다.

## 현재 구조 확인
- 로그인: `src/app/api/auth/login/route.ts`, `src/app/login/login-page-client.tsx`
- 세션: `src/lib/auth/session.ts`; 세션은 DB 사용자 역할에 귀속된다.
- 토큰: `src/lib/auth/jwt.ts`; 기존 JWT에 임의 역할을 주입하지 않는다.
- 사용자 역할: USER, LAWYER, STAFF, ADMIN, SUPER_ADMIN.
- 변호사 검증: `requireApprovedLawyer()` 및 변호사 프로필 검증 경로가 별도로 존재한다.
- 기존 `docs/project-governance/AIBEOPCHIN_6_11_PROMOTION_POPUP_AND_LEGAL_COMPLIANCE_NOTICE.md`에 `DEMO_ACCESS_*` 계약이 문서화되어 있으나, 문서 존재만으로 실제 구현을 추정하지 않는다.

## 구현 계약
1. 운영용 별도 ID(alias)와 충분히 긴 비밀번호를 사용한다. 코드, 공개 저장소, 클라이언트 번들에 비밀값을 넣지 않는다.
2. 서버 환경변수 `OPERATOR_ACCESS_ENABLED=false`를 기본값으로 사용한다. `OPERATOR_ACCESS_ID`, `OPERATOR_ACCESS_PASSWORD_HASH`, `OPERATOR_ACCESS_USER_ID`는 서버 전용 값이다. 해시 검증은 현행 `verifyPassword`와 양립하도록 구현한다.
3. 로그인은 기존 rate limit, 공통 오류 메시지, 보안 쿠키, 감사 로그 정책을 재사용한다. 계정이 존재하지 않거나 정지된 경우 거부한다.
4. 별도 서버 측 운영자 인증 컨텍스트에서만 다중 화면 탐색 권한을 부여한다. 관리자 및 변호사 역할의 일반 세션을 가장하거나 프런트엔드 역할 값만 바꿔 API 권한을 우회하지 않는다.
5. 화면 전환: 일반인 / 변호사 / 관리자 / 전체 기능 검증. 메뉴 표시는 운영자 컨텍스트와 서버 인가를 함께 검사한다.
6. 테스트 전용 가상 사건과 가상 사용자만 조작할 수 있다. 실제 사용자 사건, 첨부자료, 개인정보 접근에는 소유권·할당·명시적 별도 권한이 필요하다.
7. 변호사 등록상태를 허위 승인하지 않는다. 최종 법률 검토·서류 확정·외부 제출·결제·환불·영구삭제 등은 제한하고 별도 정식 계정/재확인을 요구한다.
8. 로그인·전환·읽기·실행 이벤트는 actor, target, scope, result, timestamp를 감사 기록한다. 비밀번호는 로그에 남기지 않는다.
9. 세션은 짧게 유지하고 로그아웃/운영 중단 시 즉시 차단할 수 있도록 한다. 운영 시 2차 인증과 IP 제한을 권장한다.
10. 실제 기능을 연결하기 전 권한 경계 회귀 테스트(일반 회원, 미승인 변호사, 운영자, 만료 세션)를 필수로 한다.

## 수용 테스트
- 기능 OFF일 때 운영자 ID가 인증되지 않는다.
- 잘못된 자격증명은 일반 로그인과 동일한 오류가 발생하고 시도 횟수가 제한된다.
- 운영자 인증 후 각각의 업무 흐름 메뉴에 도달한다.
- 데모 사건의 작업만 성공하며 타 사용자 실제 사건 요청은 403이다.
- 변호사 검증·재판 제출·결제·환불·삭제 권한은 입장키로 우회할 수 없다.
- 운영자 진입·화면 전환·차단 시도가 감사로그에 기록된다.

## 배포
기능 구현, 단위/E2E 검사, 보안감사 뒤 별도 PR로 병합한다. 운영자 ID·비밀번호 값은 GitHub에 제출하지 않고 배포환경의 암호화된 설정값으로만 입력한다.
